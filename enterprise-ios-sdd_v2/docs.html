Enterprise iOS Spec-Driven Development (SDD)

A reusable, agent-agnostic development framework for enterprise iOS/tvOS projects. The repository holds intent and rules; the agent executes; deterministic tooling and CI provide evidence.

2. The most important control: plan changes

A feature plan.md change is a lifecycle event. It invalidates prior assumptions about what was implemented and verified.

plan.md added/changed
        ↓
   plan fingerprint changes
        ↓
   impact analysis
        ↓
   ASK USER
   ├─ 1 Implement / reconcile + full feature SDLC
   ├─ 2 Validate existing implementation only
   └─ 3 Review impact / update artifacts, no code
        ↓
 execution evidence + tests + CI + convergence

The default helper blocks silent continuation:

./scripts/sdd-plan-change-check --feature FTR-023

Explicit modes:

./scripts/sdd-plan-change-check --feature FTR-023 --mode implement
./scripts/sdd-plan-change-check --feature FTR-023 --mode validate
./scripts/sdd-plan-change-check --feature FTR-023 --mode review
Recommended agent question: “Plan changed for FTR-023. Should I (1) implement/reconcile and run the full feature SDLC, (2) validate the existing implementation against the updated plan, or (3) review impact only?”

4. Project-level files

FileQuestion answeredTypical contents
constitution.mdWhat is non-negotiable?Architecture principles, security rules, AI rules, testing constraints.
objective.mdWhy does the app exist?Business problem, users, goals, non-goals, success metrics.
tech-stack.mdWhat technologies are approved/used?Swift/Xcode, iOS/tvOS, SwiftUI/UIKit, networking, persistence, SDKs, testing, CI, observability, feature flags.
tech-stack.yamlHow can automation reason about the stack?Structured versions, approved/prohibited dependencies, CI and testing fields.
architecture.mdHow is the application structured?Layers, modules, dependency direction, boundaries, DI.
engineering-rules.mdHow should engineers/agents work?Swift practices, testing, dependency policy, scope discipline.
security.mdWhat security constraints apply?Secrets, auth, sensitive data, logging, privacy.
performance.mdWhat are the performance expectations?Startup, memory, scrolling, network, media budgets.
quality-gates.mdWhat must pass before merge?Build, tests, lint, architecture, traceability, security.
release.mdHow does work reach users?Branches/tags, release gates, rollout and rollback.
adr/Why did we make a major architectural decision?Context, decision, alternatives, consequences, status.

7. Execution evidence

Implemented ≠ Verified.

For each plan item, execution.yaml should record objective evidence. A plan item is verified only when its status is VERIFIED and all required evidence flags are true.

EvidenceExample
Code existsExpected implementation path or symbol is present.
Behavior verifiedImplementation matches the plan and acceptance behavior.
Tests existMapped XCTest/XCUITest exists.
Tests passReal execution result, not an agent claim.
Architecture passStatic/import/module checks pass.
Scope passNo forbidden/unplanned paths changed.
CI passActual CI run or equivalent evidence.

8. Status state machine

DRAFT → READY → PLANNED → IN_PROGRESS → VALIDATING → CONVERGED → RELEASE_READY → RELEASED

Exceptional: BLOCKED | CANCELLED | SUPERSEDED

A plan change on a converged feature moves it back to a non-converged state. The new plan must be reconciled and revalidated.

9. Project bootstrap

Use the Skill package to merge the canonical SDD structure into a repository:

/path/to/enterprise-ios-sdd/scripts/sdd-bootstrap

It creates/merges the project constitution, project context, quality policies, MCP registry, agent adapters, reusable templates, scripts, Makefile, and CI workflow templates. Existing files are preserved by default, so the bootstrapped repository remains self-contained.

11. MCP recommendations

MCP should supply external context/actions; deterministic scripts and CI should remain responsible for build/test/quality truth.

MCPUse whenWhat it gives the agentRecommended permission
GitHub MCP ServerGitHub/GitHub ActionsRepository, issues, PRs, Actions, security, releasesRead-only first; narrow write scopes
Figma MCP ServerFigma/design-system workflowComponents, variables, layout, design contextRead-only for code generation; explicit write approval
Linear MCP ServerTeam uses LinearIssues, projects, comments, product contextRead-only first
Firebase MCP ServerFirebase/Firestore in stackFirebase project/backend contextRead-only first
Playwright MCPWeb/admin/browser testingBrowser automation/accessibility snapshotsControlled test environment
Internal iOS Build/Simulator MCPNeed agent orchestration of xcodebuild/simctlBuild/test/simulator/log contextLocal/test-only; scripts preferred
Community iOS Simulator MCPNeed interactive simulator screenshots/UI inspectionSimulator control, screenshots, accessibility/UI interactionsOptional; pin/review; test devices only

The repository file .sdd/mcp-registry.yaml stores these mappings. sdd-mcp-recommend reads your tech stack and selected feature plan to produce contextual recommendations.

12. MCP selection rule

Tech Stack + Feature Plan
          ↓
   Required external context?
          ↓
       MCP Registry
          ↓
 Official/vendor server available?
          ↓
   Least privilege profile
          ↓
 Human approval for writes
Do not add MCP just because it is available. Map every MCP to a concrete need in the project plan. For native iOS builds/tests, deterministic xcodebuild, xcrun simctl, and CI are preferable to making the build system depend on an MCP.
