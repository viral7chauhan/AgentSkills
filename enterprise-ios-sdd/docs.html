1. What this skill is trying to achieve

The repository, not the AI coding agent, is the source of truth. The agent reads the project rules and feature specification, creates a plan, implements the approved tasks, runs validation, and converges the code against the specification.

Stable

Project rules and architecture decisions live in version control and survive agent changes.

Traceable

Requirements connect to acceptance criteria, tasks, implementation, tests, and CI evidence.

Automatable

Scripts and CI can enforce what an agent should not merely claim.

3. Executable feature scaffolding

The framework is now intended to be executable as well as documented. Use the included script to create a standard feature directory without manually copying files.

./scripts/sdd-feature-create "Subscription Restore"

# or
./scripts/sdd-feature-create FTR-023 "Subscription Restore"
.sdd/features/FTR-023-subscription-restore/
├── spec.md
├── clarify.md
├── checklist.md
├── plan.md
├── tasks.md
├── test-plan.md
├── execution.yaml
└── status.yaml

The command only scaffolds artifacts. It must not invent product requirements or modify application code. The templates live under templates/feature/, which keeps the process portable across agents.

5. Feature example

FTR-023: Subscription Restore

spec.md Focus on what/why, not detailed technology choices.

# Feature: Subscription Restore

## Problem
Users with an existing App Store entitlement need to recover access
on a new install or device.

## Functional Requirements
- FR-023-001: User can initiate subscription restore.
- FR-023-002: Active entitlement is reflected in application state.
- FR-023-003: Pending, failed, and unavailable states are handled.

## Acceptance Criteria
### AC-023-001
Given an active subscription,
When the user taps Restore,
Then the entitlement state is refreshed and the UI reflects access.

### AC-023-002
Given no active entitlement,
When restore completes,
Then the app does not grant premium access.

## Edge Cases
- pending transaction
- network unavailable
- expired subscription
- StoreKit error

plan.md

# Implementation Plan

## Existing Components Reused
Subscription state store, entitlement protocol.

## Components to Change
SubscriptionRepository, ViewModel, UI state.

## New Components
StoreKit adapter only if an existing abstraction cannot support restore.

## Testing Strategy
Mock the repository boundary; add unit coverage for active, none,
pending, and error states.

## Architecture Impact
No new module. No third-party dependency.

tasks.md

T-023-001 [IMPLEMENTATION]
Add restore operation to repository boundary.
Refs: FR-023-001, AC-023-001

T-023-002 [IMPLEMENTATION]
Map StoreKit result into domain subscription state.
Refs: FR-023-001, FR-023-002, AC-023-001

T-023-003 [TEST]
Add tests for active/no-entitlement/pending/error states.
Refs: AC-023-001, AC-023-002

The agent should report evidence rather than simply saying “implemented.” A missing test or failed CI check is a validation gap.

Execution Verification — Did the Plan Actually Happen?

This is the Tech Lead control layer. A checked task is not proof. execution.yaml records evidence for each plan item and distinguishes IMPLEMENTED from VERIFIED.

IMPLEMENTED

The agent says the work is present. This is a progress claim.

VERIFIED

Required evidence exists: implementation, tests, validation checks, scope/architecture checks, and CI where applicable.

BLOCKED

Required evidence is missing or a required gate failed. The feature must not be treated as converged.

execution.yaml

feature_id: FTR-023

plan_items:
  - id: P-023-001
    description: Add SubscriptionRepository abstraction
    references:
      requirements: [FR-023-001]
      acceptance_criteria: [AC-023-001]
      tasks: [T-023-001]
    expected_files:
      - Sources/Subscription/SubscriptionRepository.swift
    evidence:
      code_exists: true
      behavior_verified: true
      tests_exist: true
      tests_passed: true
      ci_passed: true
      architecture_checked: true
      scope_checked: true
    status: VERIFIED

Run the structural checks with:

make sdd-execution-check FEATURE=.sdd/features/FTR-023-subscription-restore
make sdd-report

7. CI and convergence

Use a stable command surface so different agents can drive the same process.

make build
make test
make lint
make format-check
make validate
make traceability
make report

Agent validation

Compare specification, plan, tasks, code, tests, and applicable ADRs.

CI validation

Actually execute build, tests, linting, coverage, security/static checks, and other required gates.

Convergence

Find remaining gaps and create traceable remediation tasks. A feature is complete only when required evidence exists.

9. How to adopt this in a real project

Phase 1 — Baseline

Create .sdd/, constitution, objective, tech stack, architecture, quality gates, and thin AGENTS.md.

Phase 2 — First feature

Choose one medium-sized feature and run the full workflow from spec through convergence.

Phase 3 — Automate

Implement traceability and make validate; add GitHub Actions gates.

Phase 4 — Scale

Add reusable skills for review, testing, concurrency, security, performance, dependency audits, and release readiness.

Do not start by converting the entire backlog. Prove the workflow on one feature, then standardize it.
